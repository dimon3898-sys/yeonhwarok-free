# 호환성 차단을 해소하기 위한 범위 결정

## 확인된 제약

요청한 조건 두 개를 현재 증거로 동시에 충족할 수 없다: (1) 과거 GPU 성공 이미지를 변경 없이 사용, (2) 새 몽골 HISTORICAL 입력·106개 연속 도형·원본 authored 카메라와 라벨을 6초씩 정확히 재현. 이전 정상 영상이 없어서 차단된 것이 아니다. 기존 이미지의 정식 admission은 해당 역사 입력을 거부하며 새 역사 모듈과 source assets가 없다.

## 필요한 최소 변경의 제안 — 아직 구현/빌드하지 않음

- 기존 renderer와 성공한 6초 capture 실행 방식을 유지한다.
- 기존 검토된 역사 데이터 및 106개 도형을 원본 해시 그대로 정식 이미지 빌드 입력에 포함한다. 재생성하지 않는다.
- Studio adapter, Controller, Worker, profile 검증에 **정식 HISTORICAL 180프레임 승인 계약**을 연결한다. GENERAL 위장, permissive wildcard, 검증 우회는 사용하지 않는다.
- 기존 authored history 처리에 원본 글로벌 구간의 시작 상태를 전달할 정식 방법을 추가한다. [0,180), [180,360), [360,540)을 원본 속도로 평가하며 카메라·영토·라벨·발광의 진행 상태를 보존해야 한다. 현재 스키마에 없는 임의 필드를 사용자 JSON에 먼저 넣지 않는다.
- 확인된 기존 renderer 기능으로 상태를 표현할 수 있는지 먼저 최소 범위에서 조사한다. 표현이 안 되는 기능은 지원한다고 가정하지 않는다. 새 renderer는 만들지 않는다.
- 기존 build_variants 및 manifest/startup 절차로 generated 결과와 원본을 일치시킨다. generated 파일만 고치지 않는다.
- 신규 역사 180 입력 거부/승인, 원본 source hash, 세 구간 상태, Worker 전달, 출력 충돌만 무료 검증한다. 기존 6초·10초 PASS는 변경 영향이 입증된 부분만 검사하며 기본 계약을 보존한다.
- 성공 이미지 자체는 보존하고 별도 candidate 이미지가 필요하다. 새로운 후보의 GPU 성공은 과거 성공에서 상속되지 않으며 PENDING_GPU로 남는다. 현재 노드의 미해결 WebGL/EGL 문제도 별도 차단이다.

## 결정이 필요한 이유

사용자가 이번 작업에서 “성공한 6초 이미지를 그대로”, “기존 성공 이미지를 임의로 재빌드하지 않는다”, “FAIL/BLOCKED 해결 전 다음 단계 금지”를 명시했다. 위 범위는 입력 JSON 편집만으로 끝나지 않으므로 이 제안의 승인 없이 production 코드·이미지·gCube 설정은 변경하지 않았다.

필요한 결정 하나: **동일 이미지 무변경 조건 대신, 기존 정식 6초 경로의 역사 입력 및 구간 시작 상태 지원을 위한 최소 확장과 필요한 별도 이미지 준비를 허용할 것인지.** 이는 유료 GPU 실행 승인이 아니다.
